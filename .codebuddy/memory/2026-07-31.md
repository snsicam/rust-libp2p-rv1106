# 2026-07-31

## app 连接反复断开 —— 根因：QUIC max_idle_timeout 默认 10s 太短（已修复）

### 排查过程
- 日志 `p2p-camera/scripts/logs/`：`device_cam.log`、`viewer.log`、`tmp.txt`（设备端 ping 结果）。
- device-cam 反复掉线，断开原因**全部**是 `Cause: Connection error: I/O error: timed out`，
  连接时长随机（`35.2s` / `97.8s` / `356.2s`），断后重连握手也超时
  （`Handshake with the remote timed out`）。
- **先排除了链路质量**：从开发机 ping relay `124.221.175.240` 0% 丢包 / RTT 31.7ms，TCP 4001 OPEN；
  `tmp.txt` 显示**设备本身** ping relay 36 包 0% 丢包、RTT 31.6–51.8ms。
  → 网络正常，不是弱网/丢包，排除"链路差"假设。

### 根因（关键认知）
- 三端只设了 swarm 层 `with_swarm_config(|c| c.with_idle_connection_timeout(120s))`，
  但这管的是**"没有活跃 stream 就关连接"**，**管不到 QUIC 传输层自己的空闲超时**。
- `.with_quic()` 用的是 `transports/quic/src/config.rs` 默认值：
  `max_idle_timeout: 10 * 1000`（10s）、`keep_alive_interval: 5s`。
  → 只要连续丢 2 个 keep-alive（10s 无响应）QUIC 就单方面判死连接。
  在 RTT 抖动到 50ms+ 或设备 CPU 被编码占满导致事件循环卡顿时极易误杀。
- **`max_idle_timeout` 实际生效值 = 两端协商的较小者**，所以**三端必须同步改**，只改一端无效。

### 修复（已编译通过 `cargo check`）
`.with_quic()` → `.with_quic_config(|mut c| { c.max_idle_timeout = 30_000;
c.keep_alive_interval = Duration::from_secs(3); c })`，三处：
- `p2p-camera/device-cam/src/main.rs:~307`
- `p2p-camera/mobile-core/src/viewer.rs:~331`
- `p2p-camera/relay-server/src/main.rs:~78`（注意此文件无 `use Duration`，需写全 `std::time::Duration`）

另调整 device-cam 重连退避（`main.rs:59-62`）：
`RECONNECT_DELAY_BASE 3s→2s`、`RECONNECT_DELAY_MAX 60s→8s`
（原退避 3→6→12→24→…→60s，退避期间设备完全不可见，app 端表现就是"连不上"）。

### 待验证 / 遗留
- **relay-server 必须重新部署到 124.221.175.240 才生效**（只改本地代码没用）。
- 日志里 NAT 类型在 `Full Cone` ↔ `Symmetric` 间跳变，设备有 3 个网卡地址
  （`192.168.0.3` / `192.168.0.7` / `172.32.0.93`），出口端口漂移。
  若改完仍偶发断开，考虑用 `--udp-port` 固定端口稳定 NAT 映射。
- 设备端另有大量 `mpi_vo_composer: Layer 0 no free buffer to compose`（LCD VO 缺帧缓冲，
  VO fps 掉到 ~21，与网络无关，但说明 CPU/带宽吃紧，可能间接拖慢 swarm 事件循环）。

## 第二轮回合：QUIC 修复生效，但 LAN 直连仍每 ~50s 断（已做 Plan A + 固定 UDP 端口）

### 验证第一轮的修复
- 新日志（device_cam.log / relay.log / viewer.log，16:48 重启）：
  device↔relay 的 reservation 从 `08:54` 稳定到 `09:04`（10 分钟）**不再 timed out**，
  证明 QUIC 30s idle timeout 修复生效。

### 新根因：LAN 直连在多网卡/对称 NAT 环境下不可靠
- viewer 通过 mDNS 在 `192.168.0.x` 建 LAN 直连，但设备有 3 网卡
  （`.2`/`.3`/`172.32.0.93`），NAT 类型在 `Full Cone`↔`Port Restricted`↔`Symmetric` 间跳变，
  出口 IP 也不固定（`183.23.149.123` ↔ `192.168.0.3` ↔ `192.168.0.2`）。
  → LAN 直连每 ~50s 被底层网络打断（viewer 日志 `09:02:22` 升级，`09:03:13` 全断）。
- 原逻辑：LAN 直连升级后**主动 `close_connection(relay_conn_id)` 关掉 relay 电路兜底**，
  所以 LAN 一断就只剩整轮 reconnect（3s 退避 + 重建 Swarm + 重新 mDNS/握手）。

### 修复（用户拍板：A 为主 + 固定 UDP 端口；均已 `cargo check -p mobile-core -p device-cam -p relay-server` 通过）
1. **viewer.rs 不再关 relay 电路**：LAN 升级后保留中继 transport 连接，
   置 `relay_circuit_available = true`（新字段），作为备份。
2. **新增 `fallback_to_relay()`**：当 LAN 直连 `ConnectionClosed`(num_established==0) 且
   `relay_circuit_available` 为真时，经**现有 relay 重拨 circuit**（无需重建 Swarm/重 mDNS），
   复用 swarm 级 `stream_control` 重新打开三路 stream，发 `DirectUpgraded{via_lan:false}`，
   `connected` 保持 true（不触发上层 reconnect）。失败才退化为整轮重连。
   - `poll_swarm` 是 async fn（被调用方循环驱动），内部用 `return` 不能用 `continue`。
   - `stream_resolver.resolve()` 返回 `StreamProtocol`（非 Copy），被 `open_stream` 消费后
     不能在 println 复用 → 提前算 `video_name: &str` 再 move。
3. **`reconnect()` 重建 Swarm 后 `relay_circuit_available = false`**（旧备份失效，重连后再置位）。
4. **固定设备 UDP 端口**：`device-cam.toml` 启用 `udp_port = 48781`；
   `scripts/run_device_cam.sh` 命令行模式追加 `--udp-port 48781`（可用 `FIXED_UDP_PORT` 环境变量覆盖）。
   目的：稳定 NAT 映射，避免出口端口随机漂移导致 NAT 类型跳变。

### 注意
- `fallback_to_relay` 的 circuit 重拨地址用 `/ip4/0.0.0.0/udp/0/quic-v1/p2p/<relay>/p2p-circuit/p2p/<device>`；
  依赖 `connected_relay` 仍在线（LAN 升级时未关闭 relay transport 连接）。
- 若播放侧（media_viewer.rs / Android）对 `DirectUpgraded{via_lan:false}` 事件无处理，
  仅少一次状态刷新，不影响流（流已在中继上恢复）。已在 example 里 `DirectUpgraded` 已有分支。

## 第三轮回合：app 屏保断开 → "连接中→已连接" 循环（【已废弃·已回退】）
- 【废弃说明】本轮回退（2026-07-31，与第四/五轮一起）。用户确认原始 HEAD 行为（阻塞 send + 连接断后自动重连）
  本就是对的，"按重连恢复"是预期交互，不需要 try_send/自动丢帧等智能逻辑。
- 以下原始分析仅留作历史参考，相关代码改动已全部 `git checkout HEAD` 撤销。

### 现象
- 设备→relay→viewer 正常播放；**app 屏保**（或切后台）后 viewer 连接断开，
  恢复屏保（亮屏）后不断提示 `连接中→已连接→连接中` 循环 + 出现重连按键，视频不正常；
  手动按重连后视频恢复。
- 根因不在网络，在**通道背压**：屏保时 Android 停止调用 `nativePollVideoFrame`，
  接收端不再消费 → 视频帧通道积压至满。

### 两个根因点（均已阻塞 send，已改为 try_send 满丢弃）
1. **`jni_bridge.rs` 5ms 定时循环的 `video_tx.send(frame)`（crossbeam bounded(120)，第 276 行）**：
   阻塞 send 会卡住整个后台线程（含 `poll_swarm()` 的驱动），QUIC 流/连接 idle 超时断连
   → 恢复屏保后 JNI 自动重连 → 再堵再断 → 循环。这是**主因**。
   改为 `video_tx.try_send(frame)`（音频分支同步改）。
2. **`viewer.rs` `receive_frames` 的 `sender.send(packet).await`（futures mpsc channel(60)，第 1641 行）**：
   阻塞 send 会让 `receive_frames` 任务挂起、QUIC 流反压。改为 `sender.try_send`，
   满时丢弃这一帧（监控流允许丢帧），并每累计 60 帧打一条 `[Viewer] receive_frames backpressure` warn。
   - 注意 1507 行 `drain_to_latest_keyframe` 已用 `self.video_sender.try_send`（futures mpsc），无需改。

### 关键架构认知（易踩坑）
- `video_sender`/`video_receiver` 是 **futures mpsc**（channel(60)）：
  `receive_frames` 发送 → `poll_video_frame` 取。jni_bridge 的 `video_tx`/`video_rx` 是 **crossbeam** bounded(120)：
  `viewer.poll_video_frame()` 取到的帧 → `video_tx` → Android `nativePollVideoFrame` 取。
  **两处背压点分属不同 channel 类型**，修复时用对各自的 `try_send` 签名
  （crossbeam `try_send` 满返回 `Err(Full(_))`，futures `try_send` 满返回 `Err(TrySendError::Full(_))`）。

### 待验证 / 遗留
- 该修复只改 Rust 侧（Android 代码不在仓库）。需重新构建 `mobile-core` 的 Android 库 + 部署。
- 仅缓解"屏保断连"，若 Android 侧屏保时**主动调用了 `nativeDestroy`/断开**则属 app 层行为，Rust 侧无法感知，
  需 app 侧改为"屏保仅暂停拉帧、不销毁 viewer"。

## 第四轮回合：屏保恢复后"播放旧视频→静止"（【已废弃·已回退】）
- 【废弃说明】本轮回退（2026-07-31，与第三/五轮一起）。stall 自动丢旧帧逻辑已撤销，回到 HEAD 原始 `poll_video_frame` 简单 `try_recv`。
- 现象（用户确认 D 类）：app 屏保时 cam 断视频，恢复 app 后**没断连、提示播放中、没触发重连**，
  但播放的是**屏保前残留的旧视频**，播完旧缓冲后画面静止。根因不是网络/重连，是**channel 旧帧毒药**。
- 链路：屏保时 app 停拉帧 → crossbeam `video_tx` 满 → `receive_frames` 的 futures mpsc `video_sender`(60) 也满
  → 新帧全被 `try_send` 丢弃，channel 里只剩屏保前 60 个旧帧（旧帧在队头）。
  恢复屏保后 app 取帧，先取到 60 个旧帧（播 ~1s 旧视频）→ channel 空 → 静止。连接一直 `connected=true` 不重连。
- 修复（viewer.rs）：在 `poll_video_frame` 加 stall 检测。新增字段 `last_frame_poll: Option<Instant>` +
  常量 `STALL_RECOVERY_THRESHOLD = 2s`。当距上次成功取帧 > 2s（屏保/后台），判定 stall 恢复，
  **先清空 video_receiver + audio_receiver 所有旧帧**，返回 None；下一帧设备实时推来的新 IDR 立即刷新画面。
  正常播放(5ms 轮询)间隔远小于 2s，不会误触发。audio 同步清空避免音画错位。
- `cargo check -p mobile-core` 通过。rust-analyzer 对该文件的 334 条报错是宏/字节索引解析噪声，
  与 `cargo check` 矛盾，忽略（非本次引入）。
