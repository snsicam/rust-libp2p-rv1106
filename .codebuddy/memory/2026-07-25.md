## device-yolov5 独立验证工具: 完成交叉编译

- **目的**: 用户要求把 luckfox YOLOv5 例子用 Rust 重写, 作为独立软件 (`p2p-camera/device-yolov5/`), 不依赖 cam, 上板验证"框闪烁/同步出现消失/无标签"是不是 cam 的 VO SendFrame 路径导致的。**必须与 device-cam 互斥运行** (同一 sensor, ISP/rkaiq 用户态单实例)。
- **管线**: V4L2 抓帧(C shim, 直接 `/dev/video0`, 不走 MPI) → BGR → bilinear 640x640 → RKNN 推理(复用例子的 `process_i8_rv1106` 后处理, C shim `yolov5_shim.c`) → Rust 画框+COCO 类别标签(5x7 点阵字体) → 直写 `/dev/fb0` (BGR→BGRA/BGR565)。完全对齐 luckfox `main.cc` 的 `cv::cvtColor + memcpy fb0` 路径。
- **交叉编译 (已解决两个坑)**:
  1. **工具链位置**: `toolchain/` 不存在。实际在 `rv1106/luckfox-pico/tools/linux/toolchain/arm-rockchip830-linux-uclibcgnueabihf/` (`arm-rockchip830-linux-uclibcgnueabihf-gcc`, uclibc 8.3.0)。`build.sh` 已用绝对路径。
  2. **glibc/uclibc 链接冲突**: `librknnmrt.so` 是 glibc 构建, 但工具链 sysroot 是 uclibc。报错 `undefined reference to strcmp@GLIBC_2.4` 等 → 加 `cargo:rustc-link-arg=-Wl,--allow-shlib-undefined` (与 device-cam 一致, device-cam/build.rs:146 也是这么干的)。
  3. **getauxval 缺失**: Rust std (gnueabihf) 的 stack_overflow.rs 引用 `getauxval`, 但 uClibc 1.0.31 libc 不含。放在静态 lib 里因链接顺序拉不进来 → 改为在 `main.rs` 用 `#[no_mangle] #[cfg(target_arch="arm")] pub extern "C" fn getauxval` 读 `/proc/self/auxv` 实现, 保证在最终二进制内。
- **产物**: `p2p-camera/device-yolov5/target/armv7-unknown-linux-gnueabihf/debug/device-yolov5` (ELF 32-bit ARM PIE, interpreter `ld-uClibc.so.0`, 与 device-cam 完全一致 → 板子能跑)。模型 `model/yolov5.rknn` (7.3M) 已就位。
- **运行** (板端, 先停 device-cam): `device-yolov5 --model /oem/yolov5.rknn --dev /dev/video0`。`build.sh deploy` 可 scp (需设 `RV1106_HOST`)。本机无法访问板子, 上板肉眼验证结果由用户做。

## device-yolov5 capture 真正根因: MPLANE (本轮深挖日志)

- **深挖日志**: 重新编译后上板跑, 日志为 `[cap] /dev/video0 supported formats:` 表头后**没有任何格式行**即 `no supported format`。说明 `VIDIOC_ENUM_FMT` 首次调用即失败 (循环体未执行) —— 而 `QUERYCAP` 通过。这正是 **多平面 (V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE) 设备** 的典型表现: Rockchip rkisp/rkcif 摄像头节点只暴露 MPLANE, 用单平面 `VIDIOC_ENUM_FMT/S_FMT` 会 `EINVAL`。OpenCV (luckfox 例子) 能跑正是因为它自己处理了 MPLANE。
- **修复**: 再次重写 `src/capture.c`:
  1. `cap_init` 先 `QUERYCAP` 打印 driver/card/caps, 据 `V4L2_CAP_VIDEO_CAPTURE_MPLANE` 自动选 MPLANE 或单平面。
  2. 枚举/协商/`REQBUFS`/`mmap`/`DQBUF`/`QBUF`/`STREAMON` 全部按 MPLANE 实现 (NV12 有 Y/UV 两个平面, 单独 mmap; `v4l2_plane` 数组持久化)。单平面作为兜底路径保留。
  3. 协商失败兜底打印驱动当前 `G_FMT` 实际 fourcc+分辨率; `cap_get_frame` 按格式分发 (YUYV/NV12/RGB24/BGR24/MJPEG) 到各转换函数。
  4. **多设备节点探测**: 指定设备失败则自动探测 `/dev/video1..video15`, 找到首个能协商出支持格式的节点 (板子摄像头可能不在 video0)。
- **构建坑 (重要)**: 改 `src/capture.c` 后 `./build.sh` 一直 `Finished in 0.01s` 不重编, 二进制时间戳停在 10:50。原因: cargo 的 build script 缓存没把 `capture.c` 当依赖 (cc crate 的 rerun-if-changed 未被 cargo 追踪到)。解决:
  1. 在 `build.rs` 显式 `println!("cargo:rerun-if-changed=src/capture.c")` 等 (已加全部 C 源/头)。
  2. 先前误 `touch src/build.rs` 创建了 0 字节的 `src/build.rs` (cargo 只用根目录 `build.rs`, 该空文件无害但已删)。
  3. `cargo clean -p device-yolov5` 后重编, 出现 `Compiling device-yolov5`, 二进制时间戳刷新 (11:30), MPLANE 版已编入。无编译错误。
- **待办**: 用户重新 `build.sh deploy` + 板端 `run_device_yolov5.sh` 重跑, 看新日志: 应能看到 driver/card、MPLANE 标记、实际支持的格式、selected 格式、streaming started、以及 `fps/dets/drawn` 统计, 进而确认是否出图。若 MPLANE V4L2 仍拿不到处理好的 YUV (例如 /dev/video0 是 rkcif 原始 Bayer), 则需改用 MPP VI 抓帧路径 (同 device-cam 的 RK_MPI_VI_GetChnFrame)。

## device-yolov5 第二处 bug 修复: 帧处理/缩放越界 panic (看新日志发现)

- **新日志 (11:xx 版 MPLANE capture 上板跑)**: 格式协商成功! `/dev/video11` (driver=rkisp_v7 card=rkisp_mainpath) 支持 UYVY/NV16/NV61/NV21/NV12/NM21/NM12, **`selected NV12 (2304x1296)` + `streaming started`**。但首帧即 panic: `[main] panicked at src/main.rs:238:27: index out of bounds: the len is 1555200 but the index is 1555200`。
- **根因**: `cap_get_frame` (capture.c) 已把 NV12 转成**完整 BGR** (`g_bgr`, 尺寸 `cw*ch*3`=2304*1296*3=8,957,952B), 返回 `*data=g_bgr, *w=2304, *h=1296`。但 `main.rs` 旧逻辑错在:
  1. `copy_n = (cw*ch*3).min(fb_w*fb_h*3)` 只拷 1,555,200B 进 `disp_bgr`(720*720*3), 还按 2304 宽 stride 当 720 宽读 → 剪切错位;
  2. 接着 `bilinear_bgr_resize(&disp_bgr, cw=2304, ch=1296, ...)` 把只有 720x720x3 的 `disp_bgr` 当 2304x1296 寻址 → 越界 panic (index 1555200 == len)。
- **修复**: 改 `main.rs` 主循环: 直接把 `cap_get_frame` 返回的完整 BGR 帧 (`src_bgr = slice(ptr, cw*ch*3)`) 分别 `bilinear_bgr_resize` 到 `model_bgr`(640x640, 喂模型) 和 `disp_bgr`(fb_w x fb_h, 显示); 框坐标缩放从 `(cw/640, ch/640)` 改为 `(fb_w/640, fb_h/640)`; `draw_box_bgr` 维度改用 `fb_w, fb_h`。删除了错的 `copy_nonoverlapping` 行。重新编译成功 (11:37, 无错误)。
- **结论**: 摄像头 V4L2 MPLANE 路径现在完全打通 (ISP mainpath 出图), 仅剩帧后处理 bug 已修。用户重新 deploy + 板端重跑, 应能看到 `fps/dets/drawn` 统计 + fb0 出带标签的框。

## device-yolov5 第三处 bug 修复: 视频颜色不对 (看新日志发现)

- **新日志 (11:37 版上板)**: panic 已消失, 管线跑起来 `[yolov5] fps=0.5 dets=0 drawn=0` (能出图但帧率极低、未检出目标; fps 低是另一问题, 见下)。用户反馈"视频颜色不对"。
- **排查**: 看 luckfox 原版 `luckfox_pico_yolov5/src/main.cc` (line 117-185): `pixel_size==4` 时 `cv::cvtColor(bgr, disp, COLOR_BGR2BGRA)` + `memcpy(framebuffer)` —— 即 fb0 期望 **BGRA** (内存字节序 B,G,R,A)。我们的 `blit_to_fb` (main.rs bpp==32 分支) 写 `B,G,R,255` 与之**完全一致** → blit 不是问题。颜色 bug 在 `capture.c` 的 NV12→BGR 转换。
- **根因**: V4L2 MPLANE 的 **UV 平面 stride 常 > 宽度** (Rockchip 按对齐填充), 旧 `nv12_to_bgr` 用 `uvrow = uv + (yy/2)*w` (假设 stride==w)。UV stride 偏大 → 色度从错误水平位置采样 → 亮度/结构正常但颜色整体发飘/错位 (典型"颜色不对")。Y stride 也可能偏大。
- **修复** (capture.c):
  1. `open_and_setup` S_FMT 后从 `G_FMT` 读真实 `pix_mp.plane_fmt[0/1].bytesperline` 存 `g_y_stride/g_uv_stride` (打印 `[cap] strides: y=.. uv=.. w=..`)。
  2. `nv12_to_bgr` / `yuyv_to_bgr` 改用真实 stride 寻址。
  3. 加 env 兜底开关 (cap_init 读取): `YOLO_UV_SWAP=1` 交换 U/V (红蓝互换时翻), `YOLO_YUV_RANGE=limited` 用 BT.601 限幅(Studio)矩阵 (画面发白/对比低时翻)。默认 full range (rkisp 默认, 与 luckfox OpenCV 全幅公式一致)。
- **重新编译成功** (11:46, 无错误)。
- **待办/验证**: 用户 `build.sh deploy` + 板端重跑。新日志应多出 `[cap] strides: y=.. uv=.. w=..` 与 `[cap] color tweaks: uv_swap=0 limited=0`。若仍颜色不对:
  - 红蓝互换 → `YOLO_UV_SWAP=1 ./run_device_yolov5.sh ...`;
  - 发白/对比低 → `YOLO_YUV_RANGE=limited ./run_device_yolov5.sh ...`。
- **附带观察 (非颜色)**: `fps=0.5` 极低。原因大概率是纯 Rust 每帧两次双线性缩放 (2304x1296→640 与 →720) + RKNN 推理在 RV1106 软件跑很慢。若需提帧率, 后续可: ① 仅缩放一次喂模型、显示用 NV12 直送 fb(需改 fb 路径); ② 或把 resize 用 NEON/查表优化; ③ 或降采集分辨率。但首要在颜色验证。

## 根因定位 + 最小忠实修复 (14:5x 版, 已编译 build9 成功)

- **日志证据 (log/yolov5.log)**: `[cap] selected NV12 (2304x1296) on /dev/video11`; `[cap] frame sizes: stepwise min 32x32 max 2304x1296 step 8x8`; `strides: y=2304 uv=2304 (w=2304)`; `[yolov5] fps=0.5 dets=0 drawn=0`。
- **真正的根因 (三问题的共同源头)**: `open_and_setup` 的格式协商**从未真正向驱动请求目标宽高**。第一个候选 YUYV 在 video11 `S_FMT=fail`，于是兜底从 `G_FMT` 拿到驱动默认格式 NV12 **2304x1296** 就当成结果——它从未 `S_FMT(NV12, 720, 720)`。导致相机一直出 2304x1296 大帧，每帧两次纯软缩放 (→640 与 →fb)，fps=0.5；并被我之前加的 letterbox 强行拉成 fb 比例 (变形)。颜色/视频/fps 三者全错都源于此，而非色域公式。
- **关键事实**: `frame sizes` 显示 ISP **stepwise 支持 32x32 ~ 2304x1296、步长 8** —— 完全可以像原版例子 `cap.set(CAP_PROP_FRAME_WIDTH, disp_width)` 那样让相机**硬件缩放器直接出显示分辨率** (720x720), 根本不需要软件缩放。这是"忠实复刻例子"的正解。
- **最小修复 (capture.c)**:
  1. 协商改为: 先据 `VIDIOC_ENUM_FMT` 建 `supported[]` 列表, 对每个支持的候选**显式 `S_FMT(候选格式, 请求宽高)` + `G_FMT` 读回**, 用实际返回的宽高 (`aw,ah`) 作为 `g_w,g_h`。这样 video11 会 `S_FMT(NV12,720,720)` → `G_FMT` 回 NV12 720x720, 自动跳过不支持 YUYV 的 rkcif 节点 (video0-10 的 ENUM_FMT 只列 Bayer, 不再有 "S_FMT=ok actual=BG10" 的误导)。
  2. 保留 `frame sizes` / `strides` 诊断打印。
- **最小修复 (main.rs)**: 回到例子语义 — 相机帧 == 显示分辨率, 移除 `blit_letterbox` (连同函数一起删), 主循环仅 `bilinear_bgr_resize(..., 640, 640)` 一次喂模型, `disp_bgr` 直接 copy 相机帧后画框送 fb, 框坐标 `sx=sy=cw/640` 无偏移。
- **编译**: `build9` 14:51 成功, 无错误/无 unused 警告。
- **待办/验证**: `build.sh deploy` + 板端重跑。预期新日志: `[cap] selected NV12 (720x720) on /dev/video11` + `strides: y=720 uv=720`; `fps` 应大幅提升 (帧像素降到 1/5.5, 缩放次数 2→1); 画面不再变形; 颜色按 NV12 full-range 应正常。若颜色仍偏, 再单独排查 ISP 是否 limited-range (此版未保留 env 开关, 按用户"别自己发明"要求保持最简); dets 若仍 0 属模型/输入问题, 与本次三问题分开。
