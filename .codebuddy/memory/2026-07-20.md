## 关键结论: viewer 不依赖 cam 的 keyframe, cam 端 keyframe 计算已移除

### 验证事实
- **viewer 不信任 cam 的 keyframe flag**: `mobile-core/src/viewer.rs` 的 `receive_frames` 关键帧判定为
  `is_kf = Self::is_nal_keyframe(&packet.data)` (仅 viewer 自身字节扫描, H.265 IRAP 16-21 / H.264 IDR 5)。
  之前代码里曾写 `packet.is_keyframe() || Self::is_nal_keyframe(...)` 的 `||` 是冗余的, 现已去掉。
- **JNI 桥根本不转发 keyframe flag**: `mobile-core/src/jni_bridge.rs` 的 `nativePollVideoFrame` /
  `nativePollAudioFrame` 只返回 `[PTS(8B)] + [raw data]` 给 Kotlin/Swift, **不含 `flags` / `is_keyframe()`**。
  所以 cam 的 keyframe flag 在整条链路里没有任何外部消费者 (原生 APP 拿不到, 也靠自己扫 NAL 或 MediaCodec 处理)。
- **`media_viewer.rs` example** 同样只用 `is_nal_keyframe` 字节扫描做门控与 `[I]` 日志标记, 不用 `packet.is_keyframe()`。

### 用户决定 + 改动 (cam 端 keyframe 优化去掉)
用户确认: "viewer 没有使用 cam 端的 keyframe, 所以 cam 的 keyframe 是否可以优化去掉" → 可以, 已移除。
- `device-cam/src/rk_video_source.rs` `on_frame`: 不再扫描 NAL, C 回调已**完全移除** `is_keyframe` 参数
  (签名改为 `fn(chn_id, data, len, pts_us)`), `let is_keyframe = false;`。**省 RV1106 编码侧每帧 CPU**
  (viewer 只在首个 IDR 前扫描, 是有限成本; cam 原先每帧都扫, 是持续开销)。
- `device-cam/src/rk_camera.c`: 删除已无用的 `is_keyframe_h265`/`is_keyframe_h264` 函数与 `get_stream_thread`
  里的 `is_kf` 计算; `frame_callback_t` typedef 与 `g_callback` 调用均去掉 `is_keyframe` 形参 (与 Rust ABI 对齐)。
- `device-cam/src/media_source.rs` (文件模拟源, 用于无 RV1106 的测试): 同样不再计算 keyframe, 改为
  `MediaPacket::video(ts, data)` 与真实 `rk_video_source.rs` 行为一致 (viewer 字节扫描判定)。`nal_t` 仍用于参数集缓存。

### 进一步优化: 删除冗余的 `MediaPacket` 视频 keyframe 字段
- `proto/src/media_packet.rs`: 删除 `is_keyframe()` 方法与 `video()` 的 `is_keyframe: bool` 参数;
  视频包 `flags` 字节保留置 0 (仅音频包用 flags 区分 codec)。文档注释同步更新 (包格式说明 + 两处设计文档)。
- 调用方 `rk_video_source.rs` / `media_source.rs` 改为 `MediaPacket::video(ts, data)`。
- 单测 `test_video_packet_roundtrip` 去掉 `is_keyframe()` 断言, 改断言 `flags == 0`。
- 验证: `cargo check -p proto` 与 `cargo check -p mobile-core --examples` 均通过 (仅预存 warning)。
- 注: 视频包仍保留 1 字节 flags (置 0), 未从线缆格式移除 —— 因为音频包仍需该字节区分 codec, 若移除会使包头变长可变、且需协议版本对齐 + 双端协同部署, 收益有限, 故保留为保留字节。

- `device-cam/src/main.rs`: cam 端每 100 帧日志去掉 `[I]` 标记 (cam 不再跟踪 keyframe)。

## 诊断: 4G/relay 下视频卡顿根因 (码流选择)

### 现象
- LAN 直连 auto → resolved=main → 有视频流畅
- 4G/relay auto → resolved=sub → **一帧都没有** (真 bug, 待设备日志确认)
- 4G/relay `--stream main` (强制主码流) → **有视频但卡** (frame #100 45fps 1240kbps, 随后连续 `Could not find ref with POC 34/24/41...`)

### 卡顿根因 (有代码+日志双证据)
- `Could not find ref with POC` = H.265 解码器丢帧后参考链断裂 (花屏/卡), 非带宽为零。
- 丢帧发生在**设备端**: `device-cam/src/main.rs` `stream_video_to_viewer` (792-909):
  `BROADCAST_CAPACITY=100` (line 54); viewer 经 relay 消费慢 → libp2p stream 背压 → `write_all` 变慢
  → broadcast 积压超 100 → `Err(Lagged(n))` (889) 主动丢帧 + `request_idr` → viewer 收到不连续帧 → POC 断裂。
- 设计意图: **auto 模式 relay→sub / 直连→main** (relay 带宽有限只该走低码率 sub 704x576@512kbps; main 2304x1296 仅供 LAN/DCUtR 直连)。用户手动 --stream main 经 relay 卡是预期。

### 脚本修复 (本次已改)
`p2p-camera/scripts/run_media_viewer.sh`: 原 `if [ $# -ge 2 ]` 位置参数判断会把 `--stream main` 误当 `<relay> <device>`。
改为: 首参以 `-` 开头则所有参数原样透传给 binary (config+flag 模式), 否则才按位置参数 `<relay> <device> [port]` 解析。
另注: 脚本从项目根运行, 加载的是**根目录 `viewer.toml`** (无 stream 字段→默认 auto), 而非 `scripts/viewer.toml`。

### 待办: sub 无视频定位 (需设备端日志)
下一步让用户跑 auto 并抓 device-cam 日志, 看 `New SUB video viewer`/`Requested IDR ...(sub,chn=1)`/`frame #.. sub`/`LAGGED ..sub`/`Video stream (sub) ended (N frames sent)`, 三种可能:
1. sub 0 帧 → rk_video_source sub 通道没产出 (设备编码器)
2. sub 有帧但 viewer 收不到 → viewer 接收/协议
3. sub 也 Lagged → sub 码率仍偏高或 relay 太差

### sub 无视频根因已定位 + 修复 (本轮)
**根因 (viewer 端时序 bug)**: `media_viewer.rs` 原顺序: open video stream → open audio stream (981 `.await`) → **之后**才 `spawn(receive_frames(video))` (996)。
若 audio 的 `open_stream(AUDIO)` 在 relay circuit 上挂起 (libp2p-stream 偶发, 不 Ok 也不 Err), 则 video receive 任务永不 spawn → 无视频。
实证吻合: 最初 4G sub 日志 `Video stream opened (resolved=sub)` 后**直接结束, 连 `Audio stream opened` 都没有**; main 测试 audio 碰巧没挂起故有视频。
**设备端 sub 分发逻辑正常** (`incoming_sub.next()` → `New SUB` + `sub_tx.subscribe()` + spawn), 故问题不在设备端。
**修复**: 将 `spawn(receive_frames(video))` 提前到 audio open **之前** (video 接收与 audio 解耦)。`cargo check -p mobile-core --examples` 通过 (仅预存 warning)。
**待验证**: 重跑 auto (不带 --stream) 抓 viewer.log + device_cam.log, 确认 device_cam.log 出现 `New SUB` + `frame #.. sub`, 且 viewer 有视频。

### device_cam.log 对 main 卡顿的实锤 (4G/relay, --stream main)
两次测试 viewer peer 均为 `12D3KooWFqLXt...` (与 viewer.log main 测试一致), 均 `type=Other` (relay circuit 入站, 设备端视角)。
- 第1次 18.5s: 190 sent, **115 lagged**, 0 dropped; 大量 `SLOW write 1806/2656ms (likely DCUtR handshake interference on relay circuit)` + `LAGGED`
- 第2次 15s: 56 sent, **124 lagged**, 1 dropped; 末 `WRITE TIMEOUT >5s, disconnecting`
- 末尾 `DCUtR failed ... Outbound stream error` (viewer 在 4G/CGNAT, 入站 UDP 被屏蔽, 打洞必败)
**结论**: main 卡 = ①码率过高 (2304x1296 @~1044-1240kbps) relay 扛不住 → 背压 → broadcast(cap=100) Lagged 丢帧 → viewer `Could not find ref with POC`; ②**DCUtR 打洞与 relay 转发共用同一 QUIC 连接互相挤占** → SLOW write 1-3s。这正是 auto 设计成 relay→sub 的原因。后续可优化: 4G/CGNAT 确认打洞必败时设备端停止无效打洞以省 relay 带宽。

## sub 流修复后 "视频ok, 有点卡顿" 分析与处理 (本轮)

### 用户反馈
sub 修复后视频能出 (auto→sub 在 relay 下跑通), 但**有点卡顿**。用户环境: viewer 192.168.0.7, device 192.168.0.5 (LAN); 但 config 强制 `network_type=4G`。`viewer-ok.log` 是 LAN 直连 main 流 (30fps 流畅), 非卡顿那次。卡顿那次应为 **4G/relay 下的 sub 流**。

### 卡顿根因分析 (relay 场景)
1. **sub GOP=50 @ 30fps ≈ 1.67s 才一个 IDR**: relay 有丢帧时, 丢一个 P 帧→解码器冻结到下一个 IDR (最长 1.67s) → 周期性卡顿。这是 relay 卡顿最常见根因。
2. **DCUtR 打洞干扰 relay 带宽** (main 测试已实锤 SLOW write 1.8-2.6s, device 端检测 viewer NAT=PortRestrictedCone 故持续尝试, 但 viewer 4G/CGNAT 入站 UDP 被屏蔽必败)。属一次性 ~17s 窗口, 非持续卡顿主因。
3. **播放器无帧率 pacing/抖动缓冲**: `present_vsync()` 每帧到达即呈现, relay 突发到达→一顿一顿。

### 已做改动 (安全, 两场景无害)
`p2p-camera/scripts/device-cam.toml` `[video.sub]` `gop = 50` → `25` (关键帧间隔 1.67s→0.83s), 丢帧后解码器恢复更快。需**重启 device-cam** 生效。

### 待办 / 进一步优化 (视卡顿日志而定)
- 让用户跑 auto (4G/relay) 抓 **viewer.log + device_cam.log**, 看 `frame #.. sub` / `LAGGED ..sub` / `SLOW write` 数字, 确认是否仍 Lagged 或 DCUtR 干扰。
- 若仍卡: ① 加播放器抖动缓冲 (200-500ms) 平滑 relay 抖动; ② 抑制 DCUtR 重试 (viewer 4G/CGNAT 打洞必败时停打洞省带宽); ③ sub 码率 512→384 给 relay 更多余量。

## 卡顿根因实锤 + DCUtR 失败退避修复 (本轮, 基于真实日志)

### 日志证据 (device_cam.log + viewer.log, 2026-07-20 06:19-06:21, 4G/relay 真实跨网)
- 连接: viewer 经 **relay circuit** (relay=101.35.90.171), DCUtR 打洞**必败** (viewer 4G/CGNAT 入站 UDP 被屏蔽, 握手超时 `Handshake with the remote timed out`)。
- 设备 sub 实测 **1280x720 @ ~1024kbps** (注意: 设备实际部署配置 ≠ 仓库两份 device-cam.toml, 仓库 sub 是 704x576@512)。
- 卡顿那次 (Run B): 设备 `SLOW write` 938/2197/1788/1578/2011/2533/1470ms, 全部集中在 **DCUtR 握手窗口内** (06:21:20→06:21:36 超时); 广播 `LAGGED` 累计 **125 lagged / 171 sent ≈ 42% 丢帧**; `WRITE TIMEOUT >5s` 断开; viewer 跌到 **8-12 fps** + `Could not find ref with POC` 解码花屏。
- 对照 Run A (同 1024kbps): 仅零星 SLOW write, viewer 达 30fps —— 证明 relay 带宽本身够, **卡顿是 DCUtR 打洞干扰中继写入所致**。

### 根因
设备端 DCUtR 是常开 `dcutr::Behaviour`, 每次 relay 连接建立自动打洞; viewer 4G 入站 UDP 被屏蔽→打洞必败且握手期间挤占中继视频流写入 → 1-2.5s `SLOW write` → 广播缓冲溢出 → 42% 帧丢弃 → viewer 卡顿/花屏。且 `WRITE TIMEOUT` 断开→重连→再打洞→再卡, 恶性循环。

### 已做代码修复 (已 cargo check 通过)
1. **设备端 DCUtR 可开关 (Toggle)**: `device-cam/src/behaviour.rs` `dcutr: Toggle<dcutr::Behaviour>`; `config.rs` 新增 `enable_dcutr` (默认 true); `main.rs` 透传 + 按 peer 累计 DCUtR 失败, ≥2 次打印明确提示 "建议设 enable_dcutr=false"。两份 `device-cam.toml` 已加 `enable_dcutr = false`。
2. **viewer 端失败退避**: `media_viewer.rs` 新增 `SessionEvent::DcutrBackoff`; `run_viewer_session` 累计 DCUtR 失败 ≥2 次经事件通道上报, main 收到后下次重连 `enable_dcutr=false` (仅走中继)。无需手动配置。

### 用户部署要点 (关键!)
- 设备端读取的是**部署在 RV1106 上的那份 device-cam.toml** (sub=1280x720@1024, 非仓库两份), 用户必须在该配置加 `enable_dcutr = false` 才会生效 (仓库默认 true)。
- 需**重新交叉编译并部署** device-cam + media_viewer 二进制, 重启后 DCUtR 关闭, SLOW write 应消失, 中继应恢复 ~30fps。
- 验证: 重跑 auto, 看 device_cam.log 是否还有 `SLOW write` / `LAGGED`, 及 viewer fps 是否回到 ~30。

### 仍可能需优化 (若关 DCUtR 后仍偶发卡)
- 播放器加抖动缓冲平滑 relay 抖动; sub 码率 1024→512 给 relay 更多余量; GOP 已建议 25。

## 第十轮: 对照 RV1106 rkipc 重写 fps/idr 逻辑 (修正第九轮)
- **参照 `RV1106_Linux_SDK/project/app/rkipc/rkipc/src/rv1106_ipc/video/video.c`** 得出的正确结论:
  - **VENC 的 `fr32DstFrameRate` 是真正生效的丢帧字段** (第九轮误判"只用于码率预算、不丢帧"是错的!)。SDK 对分数帧率就是用 VENC `u32SrcFrameRate=sensor_fps` + `fr32DstFrameRate=目标` 让编码器丢帧。
  - **SDK 从不调用 `RK_MPI_VENC_RequestIDR`**, IDR 完全靠 GOP 自然出 (ini `refresh_time_s` 周期刷新)。所以"强制 IDR"的正确做法是**短 GOP**, 而非依赖 RequestIDR。
  - SDK 帧率控制在 **VI 通道层 (每码流一个 VI) + VENC 层**, 不在 VPSS。
- **Issue 2 (fps=20 实测 30) 真正根因 (两层)**:
  1. `rk_video_source.rs` 把 `sensor_fps = main.src_fps_num/den` (即 main 的**配置** fps) 传给 `rk_camera_init`, 而非 sensor 原生帧率。第九轮又把 VI 设成 `vi_fps=max(各路配置fps)`、VENC `src==dst==目标` → ratio=1 不丢帧 → 跑满 sensor 原生 30fps。
  2. **正确修法**: 新增根配置 `sensor_frame_rate`(默认 30, 对标 SDK `isp.0.adjustment:fps`), 通过 `RkVideoSource::new(..., sensor_frame_rate)` 传入; VI 全速=sensor_frame_rate; VPSS 恢复全透传; **VENC `u32SrcFrameRate=sensor_frame_rate`(真实输入率)、`fr32DstFrameRate=各路目标帧率`** → 编码器按目标丢帧。这才是 SDK 的标准分数帧率路径。
- **Issue 1 (request_idr 不出真 IDR) 正确修法**: 删掉第九轮"失败重试"的无意义逻辑; `rk_camera_request_idr` 保留单次 `RK_MPI_VENC_RequestIDR` 作 best-effort, 但**真正保证靠短 GOP** (部署 toml sub/third `gop=15` ≈0.75s 一个 IDR)。viewer `IDR_WAIT_TIMEOUT=5s` 仅作旧二进制安全网。
- **已改文件**: `rk_camera.c`(vpss 透传 / venc src=sensor_fps / request_idr 简化), `rk_video_source.rs`(sensor_frame_rate 字段+使用), `config.rs`(新增 sensor_frame_rate), `main.rs`(传参), `device-cam.toml`+`scripts/device-cam.toml`(加 sensor_frame_rate=30, sub/third gop=15)。`cargo check -p device-cam` 通过。
