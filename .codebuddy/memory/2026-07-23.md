## LCD 降 CPU 架构分析（用户问：RV1106 能否加一路码流给 LCD）

- **概念澄清**: 代码中"三码流"= VENC chn0/1/2, 输出的是 **H.265 压缩码流**, 不是原始像素。LCD 需要 BGRA 原始像素 → "用第三码流喂 LCD" 不成立(需先 VDEC 解码, 且 960x540≠720x720)。
- **RV1106 能力**:
  - VENC 编码码流硬件上限 **3 路**, 已用满, 无法加第 4 路 VENC 码流。
  - VPSS 支持 **4 通道** (`VPSS_MAX_CHN_NUM=4`, mpi.txt:4490), 目前只用 CHN0/1/2, **CHN3 空闲**; 但它是原始缩放帧(YUV/BGRA), 不是"码流"。
  - RV1106 VPSS **支持输出 `RK_FMT_BGRA8888`** (mpi.txt:3598), 内部用 SDK 单例 RGA 做 CSC。
- **CHN3 USER 给 LCD 被挡**: RV1106 仅 1 个 VPSS Group, 同 Group 内 AUTO(绑 VENC)+USER(LCD GetChnFrame) 混用 → MPP buffer 崩溃 (已实测回退, 见 2026-07-22.md)。SDK 示例(mpi.txt:3607)也是 4 通道统一 USER。故 VPSS CHN3 方案当前走不通。
- **正确降 CPU 方向**: 改走 **DRM/VOP 硬件图层** — 把 ISP selfpath 的 NV12 直接送 LCDC video overlay plane, 由显示控制器硬件做 CSC+缩放, 零 RGA(避开单例冲突)、零 CPU。需把 /dev/fb 换成 libdrm 原子 plane。这是 Rockchip camera preview 正统做法。用户尚未确认是否动手。

## bugfix: VO "Layer 0 no free buffer to compose" 狂刷日志

- **现象 (2026-07-23 上板日志 device_cam.log)**: `mpi_vo_composer ... {vo_comp_get_fb :121} Layer 0 no free buffer to compose` 每秒数条不停打印。
- **根因**: `lcd_vo_thread` 用紧循环每取到 VI selfpath 帧就 `RK_MPI_VO_SendFrame`, 而 selfpath 投帧速率=`sensor_fps=30` > VO 合成器消费速率(原 `layer.u32DispFrmRt` 硬编码 25)。投喂速率 > 合成速率 → VO 图层合成缓冲池被填满, 合成线程拿不到空闲 buffer → 狂刷上述错误。
- **修复 (rk_camera.c)**: ① 新增全局 `g_lcd_fps`(默认 20), `set_vo_config` 写入; ② `lcd_vo_init` 中 `layer.u32DispFrmRt = g_lcd_fps`(跟随配置帧率, 不再硬编码 25); ③ `lcd_vo_thread` 加喂帧限速: 距上次送帧不足 `1000/fps` ms 则 `RK_MPI_VI_ReleaseChnFrame` 直接丢弃并 continue(预览可接受丢帧), 仅按显示帧率送帧; `SendFrame` 保持 `-1` 阻塞作背压。这样投喂速率 ≤ 合成速率, 缓冲池不再溢出。
- **验证**: `build_device_cam.sh rv1106` 编译通过。需上板确认日志不再刷该错误、预览仍正常。

## 修正: VO 预览 fps=11.9 (非视频帧率, 且低于配置 20)

- **概念澄清**: `[LCD_STAT] VO: fps` 是 **LCD 预览送帧速率** (selfpath→VO), 与三路编码视频流 fps(各 20) 完全独立。用户误以为它是视频帧率。
- **根因**: ① selfpath VI 通道建通道时**未设帧率**, MPP 拒帧率控制 (日志 `dev(0) ch(1) illegal param s32SrcFrameRate(0) s32DstFrameRate(0)`), selfpath 跑在不受控默认 ~30fps; ② 上一轮应用层 50ms 限速有**量化缺陷**: 30fps 离散投帧遇 50ms 阈值会"隔帧丢一帧"→ 实测 ~15fps(11.9 含抖动)。
- **修复 (rk_camera.c)**: ① 新增全局 `g_sensor_fps`(vi_chn_init 写入); ② selfpath `vi_attr.stFrameRate` 设为 `s32SrcFrameRate=g_sensor_fps, s32DstFrameRate=g_lcd_fps`, 让 selfpath **均匀按 20fps 投帧** (消除 illegal param 告警); ③ VO 线程限速阈值改为目标间隔的 **90%** (`(1000000/fps)*9/10`), 保证均匀 20fps 投帧全部通过、仅突发时丢帧作背压; ④ SendFrame 返回值判错。→ 预期预览稳定 ~20fps, 不再溢出。
- **验证**: `build_device_cam.sh rv1106` 编译通过(11:23)。需上板确认 LCD_STAT 显示 ~20fps 且 `no free buffer` 不再出现。

## 推翻: "喂太快溢出 + 90%限速" 判断错误, 改为"VO 显示缓冲池太小"

- **上板复测 (11:3x 日志)**: 仍刷 `no free buffer to compose`, 且 `[LCD_STAT] VO: fps=9.2` (低于配置 20)。用户确认视频流实际 20fps 正常 → 编码管线无问题, 问题仅在 selfpath→VO 预览路径。
- **结论修正 (关键, 之前判断错)**: "no free buffer to compose" 来自 VO composer 内部, 指**图层显示缓冲池(u32BufLen, 范围[3,15], 由 `RK_MPI_VO_SetLayerDispBufLen` 设置, 默认偏小)** 被填满、composer 拿不到空闲 buffer。视频流 20fps 正常说明 ISP/VI 健康; 预览 9.2fps 是**结果不是原因**——`SendFrame(-1)` 因 VO 缓冲池满而阻塞等待, 连带拉低统计 fps。
- **官方 sample 铁证**: `simple_vi_get_frame_send_vo_rv1106.c` 是**紧循环 `GetChnFrame→SendFrame(-1)→ReleaseChnFrame` 无限速**, VI 通道甚至不设帧率, `u32DispFrmRt=25`, 从不刷 no free buffer。证明 `SendFrame(-1)` 自带**阻塞背压**, **"送太快溢出"假设不成立**; 我加的 90% 时间限速是画蛇添足, 反而把 fps 错误压低。
- **真因 + 修复 (rk_camera.c)**: ① **去掉 VO 线程 90% 时间限速**, 恢复 sample 式紧循环 (SendFrame(-1) 原生背压); ② `lcd_vo_init` 在 `EnableLayer` 之前调用 `RK_MPI_VO_SetLayerDispBufLen(g_lcd_vo_layer, 8)` **调大显示缓冲池到 8**, 吸收重负载(主编码并行)下 composer 偶发卡顿, 消除 no free buffer。selfpath 帧率 src=30/dst=20 保留 (均匀 20fps 预览)。
- **验证**: `build_device_cam.sh rv1106` 编译通过(11:42)。需上板确认: `no free buffer` 消失, `LCD_STAT` 回到 ~20fps。
- **经验**: Rockchip VO 预览类问题优先查 `SetLayerDispBufLen`(显示缓冲池) 与参照官方 sample 的 SendFrame(-1) 背压, 不要自加应用层限速。

## 黑屏事故: SetLayerDispBufLen(8) 导致 EnableLayer 失败

- **现象 (11:4x 上板)**: LCD 黑屏, 网络视频正常, 无 LCD 日志。日志关键报错:
  `mpi_vo {RK_MPI_VO_EnableLa:926} VoLayer not enough displaybuf buf len = 8`
  `mpi_vo_chn {RK_MPI_VO_DisableC:455} VoLayer 0 is not enabled yet`
- **根因**: 该平台 VO **显示缓冲内存有限**, 把 `u32BufLen` 设成 8 帧(720x720 RGB888) 时, `RK_MPI_VO_EnableLayer` 分配不出内存 → 返回 "not enough displaybuf buf len" → VO 整体初始化失败 → 黑屏。文档虽写范围 [3,15], 但 8 已超该平台显存上限。**调大缓冲池此路不通**。
- **更深结论**: 之前实测 composer 只能稳定消费 ~9~10fps, 说明 **LCD 实际刷新/合成能力约 10fps**(硬件事实), 无法靠软件或加大缓冲突破。投喂 20fps > 消费 9fps 是 `no free buffer` 反复出现的本质。
- **最终修复 (rk_camera.c)**: ① **删除 SetLayerDispBufLen 调用**(恢复默认缓冲, 不再黑屏); ② 把 `SendFrame(-1)`(永久阻塞) 改为 **`SendFrame(0)`(非阻塞)**: VO 显示缓冲满时立即返回失败, 线程直接 `ReleaseChnFrame` 丢帧 continue。这样**投喂速率自动等于 composer 实际消费率**, 缓冲池永不堆积, 从根上消除 `no free buffer`; 预览 fps 自然落在 LCD 实际能力 (~9~10fps)。
- **验证**: `build_device_cam.sh rv1106` 编译通过(11:50)。需上板确认: 不再黑屏、无 `no free buffer`、LCD_STAT 显示 LCD 实际可达帧率(预期 ~9~10fps, 受 LCD 刷新限制, 非 bug)。
- **经验(修正上一条)**: 此平台 **切勿调大 VO 显示缓冲(buf len)**; 预览 fps 上限由 LCD 刷新率决定, 用 `SendFrame(0)` 非阻塞丢帧匹配即可, 不要瞎限速也不要堆缓冲。

## viewer 修复：默认窗口最大化 + 流升级后视频卡死

- **需求**: ① 窗口默认打开即最大化; ② 看 viewer.log 发现视频卡死。
- **卡死根因 (viewer.log 实证)**: 连接经中继 sub 流播放后, LAN direct 触发 **sub→main 流升级**。但 `media_viewer.rs` 的 `DirectUpgraded` 事件处理**只打印日志、未重置播放器解码器门控** (`waiting_for_keyframe`)。新 main 流开头是 GOP 中段帧, 被直接喂给 ffmpeg → 一连串 `PPS id out of range` / `Error parsing NAL unit`, 仅解出 1 帧(1280x720)就花屏/卡死。cam 侧其实**每次新流建立都已 `request_idr(chn)`** (`device-cam/src/main.rs:874`, VIDEO_MAIN→chn0), 但 viewer 没等这个 IDR。
- **修复 (media_viewer.rs, player feature)**:
  1. 窗口默认最大化: 仅 `window(...).resizable().maximized().build()` **不够** — WindowBuilder::maximized() 标志在 Linux/X11 等 WM 下**不会让窗口一出现就真正最大化** (表现为"小窗口, 连接视频/手动后才像最大化")。改为 build 后对 `canvas.window_mut().maximize()` **运行时强制最大化** (`mut canvas`)。并在 `upload_frame` 首帧尺寸设置处跳过 `set_size/set_position`: 判定条件除 `window_flags() & 0x00000080` 外, 再加"窗口当前尺寸 ≥ 屏幕可用区 0.9 倍"兜底, 避免 WM 标志位首帧未置位时把最大化窗口改回视频原始尺寸。**用户澄清: 需求是"打开软件窗体即最大化", 而非"连接视频后再最大化"。**
  2. `DirectUpgraded` 处理里新增 `player.reset_decoder()`, 使升级后播放器 flush + 重新门控, 等 main 流新 IDR 再解码 (与重连行为一致)。
- **注意**: lib 侧 `receive_frames` 每个新流已有 `got_first_idr` 门控 (丢弃升级前非关键帧), 与播放器门控双重保险。sub 流(gop=15)首连 "No IDR within 5s" 为既有现象, 首连 `reset_decoder` 已覆盖, 本次未改。
- **验证**: `cargo check -p mobile-core --example media_viewer --features player` 通过。

## 设计取舍: 控制流是"独立子流同连接"而非"独立端口"

- **用户追问**: "spec 里是增加一路控制流, 不占用视频流的" vs "和端口层面分开有什么区别和优缺点"。
- **现状 (方案A, 已落地)**: 控制是 `CONTROL_PROTOCOL=/p2p-camera/control/1.0.0` 的 libp2p-stream **子流**, 与 video/audio 子流**共用同一条 QUIC 连接、同一个 UDP 端口**; 子流级流控/背压独立 → 控制与视频互不挤占 ("不占用视频流" 指流级隔离, 非端口级)。spec 出处: `ctrl_channel/spec.md:131/149`, `design.md:332`。
- **备选 (方案B, 独立端口/独立连接)**: 控制另起 swarm/transport 监听另一 UDP 端口单独打洞。
- **为何选 A 不选 B (本场景 P2P 摄像头 NAT/4G/弱设备)**: ① NAT 打洞只需一次 (B 要打两次, 对称 NAT/4G 二次打洞大概率失败→控制废掉); ② 只开 1 个端口 (B 需 2 个, 部署难); ③ relay 只走 1 条 circuit (B 要 2 条, 带宽/负载翻倍); ④ RV1106 只 1 套 QUIC 状态机 (B 资源翻倍); ⑤ 符合 libp2p 单连接多路复用哲学。
- **A 的代价 (可接受)**: 底层 QUIC 连接断了视频+控制同生共死 (本场景视频断必重连, 无碍); 连接级拥塞窗口共享 (控制包极小可忽略); 抓包不能单独隔离控制端口 (已有 tracing 日志补偿)。
- **结论**: 对流控隔离用子流即可, 端口级分开弊大于利。

## Bug 修复: SetEncoderConfig 返回 "invalid json" (双重帧封装)

- **现象 (用户日志)**: `[Viewer] >>> SetEncoderConfig stream=main: ...` → `[Viewer] <<< SetEncoderConfig failed: invalid json`; cam 端 `control_handler.rs:30` `serde_json::from_slice` 失败 → 返回 `ControlResponse::err("invalid json")`。
- **根因 (双重帧封装)**: `viewer.rs::send_control` 先 `let frame = encode_request(req)?` (`control.rs::encode_request` 已输出 `[4B len][JSON]`), 再 `write_frame(stream, &frame)` (`control.rs::write_frame` 又包一层 `[4B len]`)。线上字节 = `[4B][4B][JSON]`。cam 端 `read_frame` 只去掉外层 `[4B len]`, 把残余的 `[4B len][JSON]` 当 JSON 喂给 `from_slice` → 前 4 字节非 JSON → 失败。`GetEncoderConfig` 同样会失败 (同路径)。

- **修复 (`viewer.rs::send_control`)**: 去掉 `encode_request`, 改为 `let json = serde_json::to_vec(req)?; write_frame(stream, &json).await?;`; import 由 `{encode_request, read_frame, write_frame}` 改为 `{read_frame, write_frame}`。`encode_request`/`try_decode_*` 现为 proto 未使用 `pub fn`, 无 dead_code 警告 (保留无害)。

## Bug 修复: 控制下发后视频永久卡死 + viewer "control request timeout"

- **现象 (用户日志 10:08)**: cam 收到 `[ControlHandler] >>> SetEncoderConfig stream=main: H.265 2304x1296 ...` → 视频帧号停住不再增长 (永久卡死) → viewer `[Viewer] SetEncoderConfig failed: control request timeout` (5s 未收到响应)。

- **为何仅 set_encoder_config 需要**: 只有它调用 `StopRecvFrame`(与视频取流线程/帧队列死锁); get/set_image_config、get_system_config 是只读或一次性(reboot/reset), 无此依赖。
