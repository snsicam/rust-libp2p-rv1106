## 咨询: LCD 显示部分能否独立成软件 (分析, 未动手)

- **用户问**: lcd 屏显示视频部分可否独立出来做成一个软件。
- **现状耦合分析**: LCD 代码 (`rk_camera.c` 的 `lcd_vo_init/thread/deinit` + VI selfpath chn1→VO, ~200 行) 已高度自包含; 与编码管线仅共享: ① `RK_MPI_SYS_Init`(每进程各调即可) ② **ISP/rkaiq(用户态单实例, 整 sensor 只能一个进程 init, 最大耦合点)** ③ VI dev/pipe(`vi_dev_init` 有 GetDevIsEnable 判断可跳过) ④ 配置参数。
- **给出三方案**:
  - A: 独立进程伴随运行 (LCD app 只做 SYS_Init+VI chn1+VO, ISP 仍归 device-cam; 依据 RV1106 rockit-ko 内核态支持多进程各操作不同通道; 风险=启动顺序依赖 + device-cam 退出时跨进程 deinit 行为未知, 需上板验证; 且要关 device-cam 的 enable_lcd)。
  - B: 完全独立(自带 isp_init), 可单独当取景器, 但与 device-cam **互斥**(aiq 不能两进程 init)。
  - C (推荐): 先抽成独立模块 `lcd_preview.c` + `lcd_preview_start/stop` API, device-cam 继续链接不变; 同源码另出 standalone 二进制, 进程级独立(A/B)后续实验决定。
- **待用户答复目的** (代码复用→C; 独立重启→C+A; 离线取景器→C+B) 再实施。

## 补充: 三进程架构 (cam + 独立 UI + rknn), rknn 放哪

- **新约束**: 系统要同时跑 cam、独立 UI 程序、rknn。UI 是**外部独立二进制**(不在本仓库)。某功能需 LCD **局部显示**视频(视频占子矩形, 其余 UI 画控件)。
- **rknn 例子位置**: `~/samba/work/rv1106/rknn/luckfox_pico_rknn_example/example/luckfox_pico_yolov5/` (main.cc 单进程 monolith: `cv::VideoCapture(0)`抓 selfpath → resize 640x640 → `inference_yolov5_model`(吃 `input_mems[0]->virt_addr`) → `cv::rectangle` 画框 → `cvtColor`+`memcpy` 写 `/dev/fb0`)。**用户说 LCD 显示就是参考此例子**。
- **结论 (已向用户建议)**: 
  - **rknn 放 cam** — 例子里推理与 capture 同进程同循环共享 `cv::Mat`, 而 ISP/rkaiq 用户态单实例使 cam 是唯一原始帧拥有者, rknn 跟 capture 同进程(=cam)是原生写法; 放 ui 则需 cam 经 IPC 传大块像素或 ui 争 selfpath(不可行)。
  - **LCD 显示别照搬例子** — 例子用 naive `cvtColor+memcpy /dev/fb0` 软件路径(已验证 ~60%CPU/7fps 死路), device-cam 已升级硬件 VO(video plane, 零拷贝, 稳 20fps), 继续用硬件 VO。
  - **架构**: cam(selfpath→rknn 产出 bbox 元数据 + mainpath→VENC→p2p; selfpath→VO video plane 定位子矩形=局部显示) + ui(拥有 VO graphic plane/UI 框架, 经 IPC 收 bbox 元数据, 在 graphic 层画矢量检测框叠加于视频子矩形之上 + 其他 UI)。**检测框不烧进视频像素, 由 ui 在 graphic 硬件图层叠加**, 视频像素零跨进程拷贝, 仅 bbox 元数据走 IPC。
- **待用户确认**: ① 独立 UI 用什么框架(LVGL/Qt/裸 fb/DRM)→ 决定 video plane 合成方式 + bbox 元数据通道(domain socket/共享内存/DRM prime fd); ② ui 是否需要原始视频像素自己合成, 还是"VO video plane 子矩形 + ui graphic 叠加"即够(决定 cam 是否要 dma-buf 零拷贝交给 ui)。

## 更新: UI = LVGL + fb0

- **用户确认**: 独立 UI 程序用 **LVGL 框架, 渲染目标 /dev/fb0** (即 UI 独占 VOP graphic plane)。
- **架构收敛**:
  - **方案 A (推荐, 性能最优)**: 视频走 cam 的 **VO video plane** (硬件, 定位子矩形), LVGL 在 fb0 graphic plane **之上**叠加; LVGL 视频子矩形区域留透明透出下方视频, 检测框由 LVGL 画矢量对象于对应坐标。视频像素零进 fb0。
    - **上板必验风险**: Rockchip VOP 默认 video plane 在 graphic 之上, 需把 VO video plane z-order 调到 graphic 之下, 或 fb0 graphic 带 alpha 让视频区透出, 否则 LVGL 框被视频盖住。
  - **方案 B (回退, LVGL 最直观)**: cam 把视频 dma-buf 零拷贝交 LVGL, 做成 `lv_img` 图像控件嵌布局, 框由 LVGL 自然画在视频控件之上; 代价=每帧视频 blit 进 fb0 (软件路径开销, 但仅限视频子窗)。
  - **排除**: 双进程写同一 fb0 (撕裂) — 不可行。
- **rknn 接入 (不变, 放 cam)**: rknn 例子是 C++(`yolov5.cc`+`rknn_api`); cam 重活在 `rk_camera.c`(C)。新增 `rknn_infer.c`/扩 `rk_camera.c`, **独立线程**跑推理, 结果投到 IPC 共享区。cam 需把 box 从模型空间(640x640 letterbox)映射回**屏幕子矩形坐标**再发 LVGL。
- **cam→LVGL bbox 元数据通道**: 轻量**共享内存环形队列**(或 UDS), cam(Rust+C)写 / LVGL(C)读, 每帧仅数个 `(x,y,w,h,cls,score)`。
- **待用户拍板 A 还是 B** 后再定具体代码(cam rknn 线程 + VO 视频层局部定位 + 共享内存 bbox 通道)。

- **rknn 第二处段错误 — DMABUF 帧 pVirAddr 为 NULL (2026-07-24 修复)**: 时序修好后上板日志在 `[rknn] started` + 首帧 `on_frame chn=0/1` 之后立刻 `Segmentation fault`(rknn worker 线程首帧即崩)。根因: selfpath VI 通道用 `VI_V4L2_MEMORY_TYPE_DMABUF`(lcd_preview.c), DMABUF 帧的 `stVFrame.pVirAddr[0/1]` **不填充**(仅暴露 dma_buf fd), 而 `rknn_frame_cb` 直接 `memcpy` 自 `pVirAddr[0]` → 从 NULL 拷贝 → SIGSEGV。证据: SDK `test_mpi_vi.cpp:2286` 取 DMABUF 帧 CPU 地址用的是 `RK_MPI_MB_Handle2VirAddr(stViFrame.stVFrame.pMbBlk)`, 而非 pVirAddr。**修法(保留 DMABUF 零拷贝 VO, 不破坏显示)**: 不改成 MMAP(避免 VO 风险), 而是 `rknn_infer.c` 引入 `rk_mpi_mb.h`, 在 `rknn_frame_cb` 里 `uint8_t *base = RK_MPI_MB_Handle2VirAddr(frame->stVFrame.pMbBlk)`, 再 `memcpy(s->nv12, base, stride*h)` + `memcpy(s->nv12+y_sz, base+y_sz, stride*h/2)`(NV12: Y 在 base, UV 在 base+stride*h, 连续)。加 base==NULL 守卫(打印 `[rknn] WARN: Handle2VirAddr NULL` 防静默崩)。重建 `build_device_cam.sh rv1106` 通过。**教训: RV1106 上 DMABUF 类型的 VI 帧永远用 `RK_MPI_MB_Handle2VirAddr(pMbBlk)` 取 CPU 地址, 永远不要信 `pVirAddr`。**
- **rknn 静默无输出 — 加诊断统计 (2026-07-24)**: Handle2VirAddr 修复后上板不崩、视频/LCD 正常 (`PUMP_STAT fps≈16`), `[rknn] worker started` 有, 但无框、无 WARN、无 rknn_run fail——整条链路静默, 无法区分断在 回调没被调 / 帧没入队 / 推理没跑 / 检测数 0。已在 `rknn_infer.c` 加诊断: `g_cb_calls`(回调次数)/`g_cb_queued`(入队数) 计数, 首帧入队打 `[rknn] first frame queued: WxH stride=.. base=..`, worker 每 5s 打 `[rknn][STAT] cb_calls=.. queued=.. infers=.. dets=..`(无帧也打)。判读: cb_calls=0 → 泵没调回调(g_frame_cb 注册时序问题); queued=0 但 cb 有 → Handle2VirAddr NULL 或队列满; infers=0 但 queued 有 → worker 消费问题; dets=0 但 infers 有 → 模型/后处理/量化参数问题; 全正常但无框 → bbox_shm/LVGL 侧。注: 泵启动日志 `consumer?0` 只是启动瞬间快照, 之后每帧重查 g_frame_cb, 不代表回调未注册。新增 `#include <sys/time.h>`。
- **报错4 `VIDEO_FRAME_INFO_S` 字段不符**: 本机 SDK `rk_comm_video.h` 用的是 `stVFrame`(含 `u32Width/u32Height/u32VirWidth/pVirAddr[0..1]`) 而非例子里的 `stVFrameInfo`+`pu8VirAddr`/`u32Size`。已改 `rknn_frame_cb`: 用 `frame->stVFrame.u32Width/Height/VirWidth`, 并分别 `memcpy` Y 平面 `pVirAddr[0]`(size=stride*h) 与 UV 平面 `pVirAddr[1]`(size=stride*h/2) 进 NV12 缓冲。

## 框闪烁修复: 持久框缓存 + 时间平滑 (2026-07-24 续)

- **现象**: 上板后视频正常、有框, 但**静止物体框也闪**。日志 `infers≈5/5s`(≈1Hz 慢), `dets` 在 `0↔42` 反复跳。
- **根因**: 旧 `rknn_frame_cb` 画框依赖"本帧推理是否检出"(`if (bbox_shm_acquire() && snap.count>0)`)。推理慢 + 置信度阈值边缘抖动 → 单帧漏检时 `count=0` → 框消失一拍, 下一拍又有 → **闪烁**; 与缓冲竞争无关(视频本身正常说明 VO 送显时会拷贝帧, 不抢 VI 回收缓冲)。
- **修复 (`rknn_infer.c`)**: 引入**持久框缓存 `g_cache`** + `pthread_mutex`:
  - `update_box_cache()`: worker 每检出一次调用; 按 类别+IoU(>0.3) 匹配缓存做**时间平滑** (`BOX_SMOOTH_W=0.4`, 新检测权重), 同类同框位置收敛, 静止物体框不抖; 未匹配新框加入; **单帧漏检(n<=0)不动缓存**。
  - `rknn_frame_cb` 改为**每帧都画 `g_cache`** 中的框, 仅在 `now - g_cache_ts > BOX_PERSIST_MS(1500ms)` 无检出才清空(物体真正离开)。
  - `draw_boxes_on_nv12` 参数改为 `(boxes,count)` 直接吃缓存; 去除对 `bbox_shm_acquire` 画框的依赖(bbox_shm 仍 `publish` 给潜在 LVGL)。
  - 顺手优化: 预处理 `nv12_to_bgr` 改用**复用 BGR 缓冲 `g_bgr_buf`**(原每帧 malloc 1.5MB), `stop()` 释放并重置缓存。
  - STAT 加 `cache=`(当前持久框数) 便于确认。
- **编译**: `build_device_cam.sh rv1106` Finished 通过。
- **未验证(运行时)**: 上板看静止物体框是否稳定不闪 + STAT `cache>0` 且持续。若仍闪, 再排查 VO 缓冲竞争(概率低)。

## 框闪烁根因定位 + 彻底修复: 自有缓冲 + 逐物体跟踪 + 标签 (2026-07-24 第三版)

- **用户反馈(上板实测)**: ① 框仍闪; ② 全部框**同步出现/消失**; ③ **框无标题**(对比 luckfox 例子 `cv::rectangle`+`cv::putText`+`coco_cls_to_name`)。
- **真正根因 (推翻上一版假设)**: 上一版"持久缓存"后仍闪 → 视频本身不闪、只有框闪, 说明**不是逻辑/缓存问题, 而是共享缓冲竞争**: `rknn_frame_cb` 直接把框画在 **VI selfpath 环形缓冲** (`Handle2VirAddr(pMbBlk)` 的 base) 上, 而该缓冲 VO 也引用显示。VO 还没扫完这一帧, VI 就把下一帧捕获写进了**同一物理缓冲** → 框(仅 3px 细边)被新图像覆盖 → 框闪/消失; 视频"正常"只是因为新内容看起来像运动。例子不会闪是因为它画在**自己拥有的 `cv::Mat bgr`** 再拷到 fb0。
- **修复 (`rknn_infer.c` + `lcd_preview.h/.c`)**:
  1. **帧消费者回调改为可替换送显帧**: `lcd_preview_frame_cb` 新签名 `int (*)(const VIDEO_FRAME_INFO_S *frame, VIDEO_FRAME_INFO_S *out_frame, void *ctx)`, 返回 1=送 `out_frame`(回调自有), 0=送原始 VI 帧。泵 `lcd_vo_thread` 据此选择 SendFrame 目标; 始终 `ReleaseChnFrame(VI)`。
  2. **rknn 分配"自有显示缓冲池"** `g_disp_mb[DISP_POOL=3]` (`RK_MPI_SYS_MmzAlloc` 分配, uncached MMZ), round-robin 复用。回调里: 拷贝 VI→`s->nv12`(推理) + 拷贝 VI→自有缓冲 + 画框 + 填 `out_frame`(复制输入帧全部元数据, 仅换 `pMbBlk`/`pVirAddr[0/1]` 为自有 MB) 返回 1。VO 释放引用后我们仍持有 MB 可复用, **彻底避开 VI 缓冲竞争** → 框不再闪。
  3. **逐物体跟踪替代会无限累积的缓存**: `g_track[BBOX_SHM_MAX_BOXES]`(`track_t{bbox_t,last,used}`)。`update_box_cache()`: 先删 `now-last>BOX_PERSIST_MS` 的过期记录; 按 score 降序对检出框做**同类别+IoU(>0.4) 贪心指派**, 命中则平滑(`BOX_SMOOTH_W=0.3`)并刷新 `last`, 未命中且未满则新增。→ 每物体**唯一稳定框**, 各自独立过期, 不再有"全屏幽灵框 / 同步闪"。
  4. **加类别标签 (对齐例子)**: 新增 COCO 80 类名 `g_coco_names` + 自绘 5x7 点阵字体 `g_font[39]` + `draw_text_nv12`/`fill_rect_nv12`。`draw_boxes_on_nv12` 每框画彩色边框 + 顶部**标签条(框色填充 + 暗色文字 `name 92`)**。`VIDEO_FRAME_S` 无 `u32PoolId`; `pVirAddr` 是数组需按 `[0]=Y,[1]=UV` 赋值; 结构体含数组成员不能整体 `=` 赋值, 故逐字段拷贝。
- **编译**: `build_device_cam.sh rv1106` Finished 通过。
- **未验证(运行时)**: 上板确认 ① 静止物体框**稳定不闪** ② 各物体框独立出现/消失 ③ 屏上框带 `person 92` 之类标签 + STAT `track=N` 合理。若 VO 拒绝自有 MB 帧(罕见), 需改走 RGA 合成或 VO 图层叠加。
