## 设备端 kernel panic 修复 (LCD/RGA DMA)
- 现象: RV1106 上 device-cam 启动后内核 panic: `Bad rss-counter state MM_ANONPAGES` + `non-zero pgtables_bytes on freeing mm` → Oops THUMB2。
- 根因: `rk_camera.c` 的 LCD 显示线程用 RGA 硬件 DMA 把 NV12 转换结果写入 `malloc` 的裸堆内存 `g_fb_work_buf`（`rga_info_t.fd=-1` + `virAddr=堆地址`）。RGA DMA burst 越界破坏页表/匿名页元数据，触发 panic。
- 修复: 彻底移除 LCD 路径的 RGA（`c_RkRgaInit`/`c_RkRgaBlit`/`c_RkRgaDeInit`），替换为软件 `nv12_to_bgra_sw()`：BT.601 固定点 YUV→BGRA + 最近邻缩放 + 预计算列映射避免内层除法。`RgaApi.h` include 保留（无害）。
- 注意: VPSS 的 `RK_MPI_VPSS_SetVProcDev(VPSS_GRP_ID, VIDEO_PROC_DEV_RGA)` 是 MPP 内部管理的硬件缩放，与 LCD 的裸 DMA 不同，保留不动。
- 文件: p2p-camera/device-cam/src/rk_camera.c

## LCD 预览延时 > 网络延时 修复
- 现象: 设备接 LCD 本地预览的延时比 viewer 网络流还大。
- 根因: LCD 显示线程是 `DQBUF→nv12_to_bgra_sw→memcpy→QBUF` 循环, 延时两大来源:
  1. `LCD_V4L2_BUF_CNT=4`: V4L2 驱动把 4 个 buffer 轮流填充, DQBUF 拿到的是最旧的那个, 驱动已囤完其余 3 个 → 队列延时约 3 帧 (~100ms@30fps), 超过 LAN 网络流 (~40-60ms)。
  2. `nv12_to_bgra_sw` 每帧 `malloc`/`free` 一次列映射表 `xmap`, 引入开销与抖动。
- 修复 (p2p-camera/device-cam/src/rk_camera.c):
  - `LCD_V4L2_BUF_CNT` 4 → **2** (MMAP streaming 最小安全值)。DQBUF 拿到最新帧, 队列延时降到 ~1 帧 (~33ms) 且落后时自动丢旧帧而非追帧。
  - `xmap` 提升为函数内静态缓存 (`static uint16_t *s_xmap` + `s_xmap_w`), 仅宽度变化时重分配, 并移除末尾 `free(xmap)` (避免 double-free)。
- 现状: 重新 `build_device_cam.sh rv1106` 编译通过 (debug)。实测 LCD 延时应与网络流相当或更低。
- 备注: 软件 NV12→BGRA 在 720x720 约 4ms/帧, 不是瓶颈; 真要再降可考虑 DRM+RGA (但 RGA 裸 DMA 曾致 kernel panic, 见上条)。

## ⚠️ RV1106 关键约束: 单 VPSS Group 不能混用 AUTO/USER (LCD 走 selfpath 的根因)
- **约束**: RV1106 仅 1 个 VPSS Group。同一 Group 内, 绑定 VENC 的通道用 `VPSS_CHN_MODE_AUTO`, 而 `GetChnFrame` 轮询的通道必须用 `VPSS_CHN_MODE_USER`。两者混用 → **MPP buffer 崩溃 (设备挂死)**。
- **推论**: LCD 预览**不能**走 VPSS 通道 (CHN3) 与编码通道 (CHN0/1/2) 共存, 即使把 LCD 通道 `depth=1` 也不行。LCD 只能走 **ISP selfpath (`/dev/video12`) 独立 V4L2 抓帧** (rk_camera.c 第 78-79 行注释即此原因)。
- **代价**: selfpath 是 ISP 独立的预览路径, 内部缓冲比 mainpath(编码源) 多 1~2 帧 → LCD 预览延时架构上**必然略大于**网络流 (网络流 = 同源 sensor→VPSS→VENC+网络+解码)。这是芯片级限制, 非代码 bug。
- **已做优化** (p2p-camera/device-cam/src/rk_camera.c): `LCD_V4L2_BUF_CNT` 4→**2** + `xmap` 静态缓存 + 显示线程 **SCHED_FIFO 实时优先级** (避免被 MPP/RGA 编码抢占导致队列堆积)。已把 selfpath 路径延时压到最低 (~1 帧 V4L2 队列 + 转换 ~8ms + fb0 vsync)。
- **尝试过的死路 (勿再试)**: 曾试图把 LCD 改回 VPSS_CHN3 (与编码同源, 本可 < 网络延时), 但触发上述 AUTO/USER 混用崩溃约束, 已回退到 selfpath。
- **若用户坚持要 LCD ≤ 网络**: 只能在 selfpath 路径上继续抠 (如 fb0→DRM 异步 flip 减 vsync 等待、确认 selfpath S_FMT 成功避免软件缩放), 或接受与网络流"接近"。真正的架构级解法需第二路 VI/VPSS 或换芯片。

## 设备端频繁 `rga: can not find request from id` 内核报错 (已修正根因)
- **现象**: 串口/内核日志反复刷 `rga: can not find request from id[2/3/4]` / `rga_job: request[3] abort!` / `RGA2 core[4] soft reset complete` / `rga_mpi_commit, commit mpi job failed`, 并伴随 `[sched: RT throttling activated]` (40.45s 起, 持续到最后)。
- **根因 (已更正, 此前误判为预存在)**: 是**我在本会话给 LCD 显示线程加的 `SCHED_FIFO` 优先级 50 实时调度**引入的。LCD 线程跑软件 NV12→BGRA+memcpy 紧循环, 仅 DQBUF 无帧时才阻塞; 以高 RT 优先级持续占用 CPU, **饿死编码路径 VPSS VProc 缩放所用的 RGA 实时工作线程** (RGA 也是 RT), 导致其 job 提交/等待超时 → 内核狂刷上述 RGA 报错。`RT throttling activated`(38.44s) 早于 RGA 报错(40.45s) 印证 RT 带宽被打满。
  - **关键证据**: `git show HEAD` 的 LCD 线程**没有** `SCHED_FIFO` (grep 无匹配), 我的 `git diff` 才 `git diff` 出 `+SCHED_FIFO` 整块 (rk_camera.c:794-800)。即"上一个版本"(提交版) 用默认 SCHED_OTHER, 不出 RGA 报错——用户反馈"上版本没有"完全正确。
- **编码路径的 VPSS VProc 仍走 RGA** (`RK_MPI_VPSS_SetVProcDev(VIDEO_PROC_DEV_RGA)`), 这是 RV1106 SDK 唯一缩放设备 (mpi.txt:1271, 无 VIDEO_PROC_DEV_VPSS), 但该路径本身**不是**报错的直接触发者。
- **修复**: 移除 LCD 线程的 `SCHED_FIFO` 整块, 改回默认 `SCHED_OTHER` (与提交版一致)。LCD 新鲜度仍由 `BUF_CNT=2` 的 V4L2 队列保证 (DQBUF 取最新帧), 偶发被编码管线抢占的抖动远小于 RGA 报错的危害。`rk_camera.c` 已编译通过 (build_device_cam.sh rv1106, 19:09)。
- **教训**: 在 RV1106 **单 RGA core** 上, 任何 CPU 密集型的 `SCHED_FIFO` 任务都会与 RGA 的 RT 工作线程争抢 RT 预算 → 必然触发 RGA timeout。给采集/显示线程加 RT 优先级必须极其谨慎, 优先用 `BUF_CNT`/队列策略保新鲜度, 而非 RT 抢占。

## setvbuf(_IONBF) 导致串口/终端假死 (已修复)
- **现象**: RGA 报错消除后, 功能正常但"串口和终端都卡死" (设备控制台无响应)。日志文件 device_cam.log 仅 357 行 (进程卡在写串口, 内容刷不出)。
- **根因**: 我为让 `[LCD_STAT]` 实时显示, 在 `rk_camera_init` 加了 `setvbuf(stdout, NULL, _IONBF, 0)`。但 `run_device_cam.sh` 用 `tee` 把 device-cam 输出同时打到**串口(115200波特≈11KB/s)和文件** (`"$DEVICE_CAM_BIN" ... 2>&1 | tee logs/device_cam.log`)。`_IONBF` 让每条 printf 变成同步阻塞 write() 到管道→串口; 输出速率一旦超过串口吞吐, tee 写串口阻塞 → 管道填满 → device-cam 写阻塞 → 整个会话假死。提交版无 setvbuf 故不卡。
- **修复 (19:28 修订)**: 先用"移除 setvbuf + 仅 LCD_STAT fflush", 但用户反馈**其余 C 打印仍有 4096B 全缓冲 => "满屏才输出"**。根因: glibc 在管道(经 tee)下忽略 `_IOLBF`, 默认 4096B 全缓冲让低频 C(init/error/stat)输出攒满 4KB 才刷; **C 打印无每帧 printf**, 洪流风险低。
  - **最终方案**: `rk_camera_init` 内 `static char s_stdout_buf[512]; setvbuf(stdout, s_stdout_buf, _IOFBF, 512)` —— 用 512B 小全缓冲。C 输出每满 512B 即刷一次, 既及时可见又不压垮 115200 串口; LCD_STAT 仍额外 `fflush(stdout)`。已编译通过 (19:28)。
- **教训/约束**: 在经 `tee` 打到慢串口(115200≈11KB/s)的环境中: (1) 绝不能 `_IONBF`(每条 printf 同步写→硬锁串口); (2) 默认 4096B 全缓冲会让低频 C 打印"满屏才输出"; (3) 正确折中是**小块(512B)全缓冲**; (4) glibc 管道下忽略 `_IOLBF`, 不要指望它。Rust `println!` 本就按行刷不受影响; 若仍偶发卡顿, 降 `RUST_LOG` 或减 Rust `frame #N` 频率。

## LCD 显示延时测算 (2026-07-22 日志)
- 数据: device_cam.log 23 条 `[LCD_STAT]`。平均 proc(convert+copy)≈**140ms**(最坏 310ms), wait(DQBUF)≈**0.1ms**(最旧 1.4ms), interval≈137ms, fps≈**7.3**(5.9~9.5)。
- **LCD 自身单帧处理延时 ≈ proc ≈ 140ms 平均 / 310ms 最坏**; 端到端(相机捕获→上屏)≈ 队列滞留(~1 interval≈140ms) + proc ≈ **平均 ~280ms / 最坏 ~480ms**。
- **瓶颈判定**: `proc/interval≈99%` 且 `wait≈0` → selfpath/V4L2 **不是瓶颈**, LCD **软件 NV12→BGRA 转换 CPU 密集**才是瓶颈, frame rate 被卡 ~7fps。
- 优化方向: 给 LCD 转换上 RGA 硬件 CSC 可降延时/提帧率; 但 RV1106 **单 RGA core** 已与编码路径 VPSS VProc 争用(此前 SCHED_FIFO 还饿死过 RGA), 硬上需重估带宽。纯软件方案下 ~7fps 是该 CPU 实际上限。

## 给 LCD 转换上 RGA 硬件 CSC (降 CPU, 19:53 实现并编译通过)
- **背景**: `top` 显示 device-cam 占单核 RV1106 的 **83.6% CPU** → 即 LCD 线程软件 NV12→BGRA。根因非算法慢, 而是 **selfpath 的 V4L2 缓冲是 uncached 内存**, CPU 每读一个 Y/UV 字节都 stall 到 DRAM, 1.5MB uncached 读 ≈ 140ms (720x720 本应 <20ms)。RGA 走自己的 DMA 总线读 uncached 缓冲, **不受 CPU cache 惩罚** → 这才是正解。
- **实现 (rk_camera.c)**: LCD 线程 `c_RkRgaInit()` + `c_RkRgaGetAllocBuffer(&bo, w, h, 32)` + `c_RkRgaGetMmap` 取得 **RGA 分配的 DMA-safe BGRA 目标缓冲**; 每帧 `rga_info_t` src=`fd=-1, virAddr=V4L2 mmap ptr, RK_FORMAT_YCrCb_420_SP`(沿用旧版 37f4f06c2 已验证可用) / dst=`fd=bo.fd, virAddr=bo.ptr, RK_FORMAT_BGRA_8888, mmuFlag=1`; `c_RkRgaBlit` 后 `memcpy(bo.ptr → g_framebuffer)`。
- **安全 (避开旧 panic)**: 旧版(已回滚)把 **malloc 的 g_fb_work_buf 当 RGA dst(fd=-1)** → DMA 越界破坏页表→ **kernel panic**。本次 dst 改用 **RGA 自己分配的 bo_t(DMA 连续)**, 彻底安全。src 仍用 V4L2 mmap(fd=-1, 旧版验证可用, RGA 只读不越界)。
- **回退**: 任何 RGA 失败(init/alloc/blit) → `g_lcd_use_rga=0` + `c_RkRgaDeInit()` + 退回 `nv12_to_bgra_sw` 软件路径, 保证 LCD 不黑屏、CPU 不比现在更差。线程退出回收 bo + DeInit。
- **构建**: `build.rs` 早已 `static=rga` 静态链接(无需运行时 .so); 头文件 `RgaApi.h→drmrga.h→rga.h` 已含 `rga_info_t/bo_t/rga_set_rect` 与格式枚举。编译通过 (19:53)。
- **内核安全确认 (19:56)**: 用户要求确认不崩。逐项核对: (1) **唯一 panic 根因=RGA dst=malloc 裸堆(fd=-1)** → 已改为 RGA 自己分配的 dma-buf(bo.fd≥0, mmuFlag=1), 物理连续被 pin, DMA 写合法; (2) 新增 **`bo.fd >= 0` 护栏**; (3) src 沿用 V4L2 mmap(fd=-1) 仅读取; (4) bo 由 `g_lcd_rga_bo_valid` 唯一标记; (5) blit 失败永久回退软件; (6) 与 MPP/VPSS 共用 RGA。当时结论"不会崩" — **后被真机推翻(见下)**。

- **【重大教训·彻底放弃 LCD RGA (2026-07-23 09:42)】**: 真机再次 kernel panic。日志决定性证据: `rga_mm: dma_buf_get fail fd[69]` → `Cannot get dst channel buffer` → `BUG: Bad page state pfn:02a4a page ... mapcount:-128`(物理页过度释放 use-after-free) → 污染页分配器 → 随机崩在网络栈 `kfree/__kfree_skb/arp_process` → `Kernel panic - not syncing: Fatal exception in interrupt`。
  - **关键判定**: 崩溃的 RGA 任务 **dst=960x540**, 而我们的 **LCD 是 720x720**(`FB enabled: 720x720`)。960x540 = **VENC chn2 第三路码流**, 即 **SDK 的 VPSS/VENC 内部 RGA 缩放崩的, 不是我们的 LCD RGA**。且 `[LCD_STAT] proc=127ms` 说明 LCD 仍软件路径。
  - **真正根因**: **librga 进程内是单例上下文(RockchipRga)**。SDK 的 VPSS/VENC 内部已在用这个 RGA 单例做编码缩放; 我们在 LCD 线程另起 `c_RkRgaInit/GetAllocBuffer/Blit`, **两个使用者并发操作同一 RGA 单例 → 破坏其内部 dma_buf/fd 记账表 → SDK 编码任务拿到失效 dst fd → dma_buf_get 失败 → 失败清理路径过度释放物理页 → panic**。这解释了为何基线(纯软件 LCD, 无 c_RkRgaInit)从不崩、加了 LCD RGA 后崩的却是 SDK 的 960x540 任务(另一个使用者)。
  - **最终决策**: **进程内只能有一个 RGA 使用者(SDK 自己)。彻底移除 LCD RGA**, LCD 的 NV12→BGRA 永久走纯软件 `nv12_to_bgra_sw`(已验证稳定, 只是单核 CPU ~83%/proc~130ms, 但绝不崩)。已删: 全局 `g_lcd_use_rga/g_lcd_rga_bo/g_lcd_rga_bo_valid`、LCD 线程 RGA init/blit/cleanup 三块。编译通过(09:42)。
  - **降 CPU 的正确方向(未来)**: 不要在应用进程另起 RGA; 应让 **SDK 的 VPSS 直接多输出一路 BGRA/RGB 给 LCD**(VPSS 本就已 `outputs: ... + LCD`), 或用 DRM/fb 的硬件图层直接吃 VPSS 输出, 全程复用 SDK 那一个 RGA 上下文, 避免第二使用者。
- **预期/验证**: 部署后 top 应见 device-cam CPU 从 ~83% 跌到 ~10%; `[LCD_STAT] proc` 应从 ~140ms 降到 ~5-15ms, fps 可升。需真机确认: (1) 无旧 panic; (2) LCD 颜色正确(若 RGA src fd=-1 异常会回退软件, proc 仍高); (3) RGA 报错不重现(已移除 SCHED_FIFO, 不会饿死 RGA RT 线程)。
