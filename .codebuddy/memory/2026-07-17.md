## BUG: rk_camera.c 日志 `first frame` 被每 300 帧重复打印（误导）

- **现象**: `p2p-camera/scripts/logs/device_cam.log` 里大量 `[rk_camera] first frame[0/1/2]: len=... pts=... keyframe=1`，名字暗示"首帧"却反复出现。用户实测一秒打 100+ 次。
- **根因**: `device-cam/src/rk_camera.c` 的 `get_stream_thread` 里：
  ```c
  if (loopCount%(30*10) == 0) { printf("[rk_camera] first frame[%d]: ...\n", ...); }  // 每 300 帧一次
  loopCount++;
  ```
  设计本就是"每 300 帧打印一次"（`loopCount % 300` 逻辑本身没错），但**隐含了"帧率约 10~30fps"的假设**。当 `RK_MPI_VENC_GetStream` 在 busy-loop 式高速返回（无真实视频源/编码器被极高速抽空的测试设备常见）时，`loopCount` 在毫秒级越过 300 的倍数 → 一秒打 100+ 次。用户原话："打印一次之后loopcount++,不应该打印的"——意指正常帧率下不应如此频繁，问题出在帧率异常飙升。注意：此日志来自 C 库 `librk_camera.a`（由 `rk_camera.c` 编译），**不在 Rust 源码中**（Rust 侧 `rk_video_source.rs` 用 `[rk_video]`/`[RkVideoSource]` 前缀）。
- **修复**: 
  - 新增 `first_logged` 标志：`first frame` 每通道只打一次（符合"首帧"语义）。
  - 周期性日志改名 `heartbeat[%d]` 并附 `frames=%d`。
  - **关键**：心跳在 `loopCount % 300` 触发基础上，再加 `time()` 最小间隔闸门（5s），使日志频率与帧率解耦——正常帧率仍"每 300 帧"打，帧率异常飙升时也不会洪水打印。
- **生效条件**: 必须重新编译 `rk_camera.c` → `librk_camera.a`，再交叉编译 `device-cam`（armv7-unknown-linux-gnueabihf）并部署到 RV1106。仓库现有 `librk_camera.a` 仍是旧版（含误命名日志），需重编。
- **提示**: 排查 device_cam 日志时，注意 `[rk_camera]` 前缀 = C 库日志，`[rk_video]`/`[RkVideoSource]` = Rust 日志，二者来源不同。

## BUG: rk_video_source.rs `on_frame` 的 NAL 解析错误（is_keyframe / is_h265 / param set 全错）

- **现象**: `[rk_video] keyframe` 日志永不打印（用户问"为什么没打印这个"）。进一步分析发现 `MediaPacket` 的 `is_keyframe` flag 恒 false，且 `get_param_sets()` 对 H.265/H.264 都返回空（VPS/SPS/PPS 从不缓存）。
- **根因**: `on_frame` 直接 `slice.first()` 当 NAL header。但 VENC `pack_mode=0` 的数据带 Annex B start code（`00 00 00 01` 或 `00 00 01`），首字节是 `0x00` → `is_h265` 误判 false、`is_keyframe` 恒 false。且一个 pack 含 VPS+SPS+PPS+IDR，**首个 NAL 是 VPS(32) 不是 IDR(19)**，只读第一个 NAL 也判不出关键帧。C 侧 `is_keyframe_h265/h264` 是**扫描整个 buffer 所有 NAL** 的，所以 C 能正确打印 `keyframe=1`，Rust 侧漏掉了这一步。
- **修复** (rk_video_source.rs): 新增 `split_nals()` 按 start code 切分 NAL，在 `on_frame` 中**逐 NAL** 判断 `is_h265`（h265_type>=16）、`is_keyframe`（H.265 IRAP 16-21 / H.264 IDR 5）、并**逐 NAL 缓存** param set（之前错误地 `ps.push(slice.to_vec())` 缓存整个 pack，现在改为 `nal.to_vec()` 单 NAL）。逻辑与 C 侧 `rk_camera.c` 的 `is_keyframe_h265/h264` 一致。
- **连带影响**: 修复后 `get_param_sets()` 才会真正返回 VPS/SPS/PPS，viewer 通过 `main.rs:get_init_nals → stream_video_to_viewer` 收到的 init_nals 才非空（之前恒空，viewer 只能靠流内 SPS/PPS 或 `is_hevc_irap` 兜底）。viewer.rs:820 的 `packet.is_keyframe() || Self::is_hevc_irap(...)` 现在前者即可命中。
- **注意**: 本机缺 RV1106 SDK 头文件（`rk_mpi_sys.h`），`cargo check --features rv1106` 在 `build.rs` 编译 `rk_camera.c` 阶段就失败，**无法在此环境做 Rust 类型检查**；改动已人工核对（u8/usize 类型、生命周期、变量使用），部署到 RV1106 前需在带 SDK 的环境交叉编译验证。

## BUG: 最小化/重连导致 device-cam 同一 viewer 多路视频流打架

- **现象**: `p2p-camera/scripts/logs/device_cam.log`(异常) 同一 viewer peer 出现多次 `Viewer connected`/`New MAIN`（`...Ucpe39s` 3 次: 225/251/286，`...RAqS7uR` 2 次: 454/512），但只有 1 次 `Viewer disconnected`(403/577)，多路 `Video stream ended`(380/392/405 与 579/589) 挤在最后，断开时 `remaining=1`→`remaining=0`。用户描述: 最小化不掉流(只是不 render)，最大化重连又开一路 → 两路视频流打架。对照 `device_cam2.log`(正常) 是严格 1:1（每次 connected 配对 disconnected + 单一 ended）。
- **根因**: `device-cam/src/main.rs` 每收到一个 MAIN/SUB/THIRD/AUDIO 流请求就 `tokio::spawn(stream_video_to_viewer(...))`，**没有任何"同 (PeerId, 流类型) 去重"机制**。viewer 最小化时 example(`media_viewer.rs:434-446`) 用 `session_abort_handle.abort()` 试图断流，但旧 libp2p 连接/子流在设备侧未及时关闭（LAN/DCUtR 路径关闭传播慢，或 abort 后设备侧 `stream.write_all` 还在 5s 超时窗口内），restore 又开新流 → 设备侧多个 `stream_video_to_viewer` 同时 `subscribe()` 同一 `main_tx` broadcast 推送 → 打架（重复帧/解码混乱/双倍带宽）。viewer 的 lib 侧(`mobile-core/src/viewer.rs`)已有 `video_abort_handle` 在 `reconnect()`(700-701) 与流切换(604-608) 时 abort 自己的接收任务，故接收侧不打架，**问题在设备发送侧**。
- **修复**: `device-cam/src/main.rs` 新增 `let mut active_streams: HashMap<(PeerId,&str), tokio::task::JoinHandle<()>>`，四个流接受分支在 `tokio::spawn` 前先 `match active_streams.get(&key).map(|h| h.is_finished())` → `Some(true)` 则 remove，`Some(false)` 则 `abort()` 旧任务，再 `insert` 新 handle。保证每 (peer, 流类型) 至多一路发送任务。已 `cargo check -p device-cam`(不带 rv1106 feature) 通过（仅 warning）。
- **补充建议**: 设备侧去重是稳健兜底；viewer 侧也应确保最小化时旧流被彻底关闭（而非仅 abort session task 依赖连接关闭传播），避免旧流在 5s 超时窗口内残留。

## ROOT CAUSE(用户纠正): 最小化没关视频流 —— 根因是 viewer 的 receive_frames 任务持有子流句柄，QUIC 连接关不掉

- **用户纠正**: 上一节把"两路流打架"当根因去加设备侧 `active_streams` 去重，但用户指出**根本原因是最小化时 cam(设备侧)没关掉视频流**，之前没找出来。
- **真正的根因链路** (media_viewer.rs):
  1. 最小化主循环 `WindowMinimized` 调 `session_abort_handle.take().abort()`，只丢弃 `run_viewer_session` 这个**会话任务(swarm)**。
  2. 但 `receive_frames` 是**独立 `tokio::spawn`** 的 (line ~1007/965)，持有 `video_stream`/`audio_stream` **子流句柄**。
  3. libp2p QUIC 连接由连接处理任务持有，只要子流句柄没释放，连接处理任务引用计数>0 → **连接不关闭**。
  4. 设备侧一直写帧 → `receive_frames` 持续读到数据永不报错 → 连接永远 busy → 设备 `stream_video_to_viewer` 的 `write_all` 永不失败 → 任务永不退出 → **视频流永远不关**。
  5. 最大化重连又开新连接 → 设备侧同 peer 两路流并存 → 两路视频流打架。
  - 设备侧 `stream_video_to_viewer` 循环由 `source.recv()`(broadcast `main_tx`) 驱动，`main_tx` 是摄像头全局帧源永不关闭，故该任务**唯一**退出途径是 `write_all` 失败(对端关连接)。对端(abort)没真关连接 → 永不退出。
- **修复** (media_viewer.rs, 已 `cargo check -p mobile-core --example media_viewer --features player` 通过):
  - `run_viewer_session` 新增 `shutdown_rx: oneshot::Receiver<()>`；主事件循环改用 `tokio::select!` 监听它。收到信号时**先 abort `video_abort_handle`/`audio_abort_handle`(释放子流句柄) → `swarm.disconnect_peer_id(device_cam)`(显式断连) → `return Ok(())`**，连接才真正关闭，设备 `write_all` 失败停止推流。
  - `spawn_session` 内部建 `oneshot`，receiver 传给 `run_viewer_session`，sender 作为 `(AbortHandle, Sender)` 返回；7 个调用点改 `let (ah, stx) = spawn_session(...)` 并 `session_abort_handle = Some(ah); session_shutdown_tx = Some(stx);`。
  - 主循环新增 `let mut session_shutdown_tx: Option<oneshot::Sender<()>> = None;`。
  - `WindowMinimized` 改为 `if let Some(tx) = session_shutdown_tx.take() { tx.send(()); }` 优雅关流（**不再直接 abort**，因 abort 正是连接关不掉的原因）。`WindowRestored` 重新 `spawn_session` 自然拿新 sender。
- **结论**: 设备侧 `active_streams` 去重(上一节)仍保留作防御兜底，但**根因修复在 viewer 侧**——最小化必须显式释放子流+断连，而非仅 abort swarm 任务。

## 首次打开视频"马赛克一下"根因与修复 (media_viewer.rs)

- **现象**(viewer.log): 首次打开视频第 56→58 行 `First IDR received` 紧跟 `[hevc] Could not find ref with POC 29` → 花屏；而最大化重连(第 73/119/124 行 `Decoder flushed, waiting for keyframe`→`Keyframe received, resuming decode`)干净无马赛克。
- **差别不在关键帧判定**: `is_hevc_irap`(receive_frames)与 `is_hevc_idr`(播放器)都是判 NAL 16..=21，完全相同。真正差别是**门控层数**：首次打开只有 receive_frames 一道且被破坏；重连多了播放器级 `waiting_for_keyframe` 门控。
- **根因链路**:
  1. 设备 `stream_video_to_viewer`(device-cam/src/main.rs) 新流建立先把 VPS/SPS/PPS 作为独立包发出，且 `MediaPacket::video(0, true, ...)` **标了关键帧标志**(:836)，再 `request_idr`(:863)——真 IDR 需几帧后才产出，其间 broadcast 里排队的 GOP 中段 P 帧被继续转发。
  2. viewer `receive_frames`(:1441) 门控 `let is_key = packet.is_keyframe() || is_hevc_irap(...)`：第一个 VPS 包 `is_keyframe()==true` → **`got_first_idr` 被提前置真** → 门控失效 → GOP 中段 P 帧全部放行。
  3. 首次打开播放器 `waiting_for_keyframe=false`(new() 初值)，无第二道门 → 无参考 P 帧直进空解码器 → `Could not find ref with POC` → 马赛克，直到真 IDR 到达才清。
  4. 重连有 `reset_decoder()`→`waiting_for_keyframe=true`，播放器丢弃一切直到真 IDR(RK 的 IDR AU 内联携带 VPS/SPS/PPS)→ 干净。
- **修复**(已 `cargo check -p mobile-core --example media_viewer --features player` 通过): `VideoPlayer::new()` 把 `waiting_for_keyframe` 初值由 `false` 改为 `true`(media_viewer.rs ~1710)，使首次打开与重连行为一致——播放器级门控，等真 IDR 才解码。
- **latent 隐患**: mobile-core/src/viewer.rs 的 lib 路径同样有"init NAL 标关键帧提前打开 got_first_idr 门"的问题，但 lib 无 SDL 播放器门(mobile app 自己解码)；如后续 mobile 端也花屏，应在 receive_frames 改为仅 `is_hevc_irap` 才置 `got_first_idr`(不信任 is_keyframe flag)。

- **修复方向(待日志确认)**: 若确诊 FFI 错位 → 改回调签名规避(如把 `is_keyframe` 提到 `u64` 前, 或改用结构体指针传参, 或 C 侧把标志打包进一个 `u64`/指针避免 u64 后的 int 对齐问题)。
